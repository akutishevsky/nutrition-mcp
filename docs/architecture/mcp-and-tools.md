# MCP Server, Tools & Data Rules

## Project Overview

nutrition-mcp is a Model Context Protocol (MCP) server for nutrition-related functionality, built with Bun and TypeScript. Entry point is `src/index.ts`. It runs on MCP TypeScript SDK **v2** (`@modelcontextprotocol/server` at runtime; `@modelcontextprotocol/client` in tests and in the web dashboard's in-process tool calls, `src/dashboard-api.ts`, so it is a runtime dependency) with Zod 4 as an explicit dependency; `@modelcontextprotocol/sdk` v1 is gone, so import `McpServer`, `InMemoryTransport`, `createMcpHandler` from `@modelcontextprotocol/server`. Every `inputSchema` / `outputSchema` here is a schema object (`z.object({…})`), never a raw shape: v2 still auto-wraps raw Zod 4 shapes via a deprecated overload, but the explicit form is the supported path, and it lets the exported `*_OUTPUT_SCHEMA` constants be `.parse()`d directly in tests. `/mcp` is a dual-era endpoint built on `createMcpHandler` (`src/mcp.ts`): it serves the `2026-07-28` revision (per-request `_meta` envelope, `server/discover`, no protocol-level sessions, `Mcp-Method` / `Mcp-Name` routing headers validated against the body) and, through the default `legacy: "stateless"` fallback, still answers `2025-11-25` clients with the same per-request `initialize` idiom the old hand-rolled transport used — one server factory backs both eras. The factory gets no Hono context: the authenticated user travels in the `authInfo.extra.userId` pass-through from `handleMcp`, and the public origin (for the icon URL) is read from `ctx.requestInfo`. The "/mcp over HTTP" section of `src/mcp.test.ts` drives both eras in-process by pointing a v2 `Client`'s `fetch` at the Hono route — there is no in-memory transport for the modern era, so that is the only way to test it. It lives inside `mcp.test.ts` deliberately: `mock.module` is process-wide, and a separate file with its own mock/restore of `./supabase.js` broke `middleware.test.ts`'s mock on Linux CI (not reproducible on macOS). Two rules follow: stub `./supabase.js` from an existing mock window rather than opening another, and restore from a snapshot taken **before** `mock.module` — Bun patches the namespace in place, so restoring from the live import is a no-op. `listChanged` is advertised `false` on purpose: the endpoint is stateless and refuses GET, so no channel exists to deliver a list-changed notification. Two v2 wire facts worth knowing: advertised schemas are JSON Schema 2020-12 (v1 stamped draft-07), and a POST whose `Content-Type` is not `application/json` is answered `415` before the body is read. Server version must be updated in three places: `package.json`, `src/mcp.ts` (McpServer constructor), and `server.json`. The server icon is at `public/favicon.ico`. Tool call analytics (duration, success/failure, error category) are tracked via `src/analytics.ts` and persisted to a `tool_analytics` Supabase table. Each row also carries `protocol_era` and `client_name`, because the runtime access log is a ring buffer holding well under an hour of traffic and cannot answer whether anyone still uses the 2025-era leg; retiring it is gated on `select count(distinct user_id) from tool_analytics where protocol_era = 'legacy' and invoked_at > now() - interval '30 days'` reaching zero — distinct **users**, over a window long enough to include people who log weekly. `client_name` is present on every modern call but only on a legacy `initialize`, since the stateless legacy leg builds a fresh server per request and only that one carries `clientInfo`. Runtime log lines (`console.*`) never carry a user id, email or per-user path; that is a privacy-policy promise, pinned by `src/log-privacy.test.ts`, and `analyticsLogLine` is the only analytics log formatter. Per-user questions go to `tool_analytics`.

**Registered tool set.** `src/mcp.ts` has 53 `server.registerTool()` calls; the number is hand-typed in a dozen places and every one must move together when a tool is added, removed, or renamed. Beyond `src/mcp.test.ts` and `README.md`'s MCP Tools table, the count lives in `src/copy/tools.ts`'s `TOOLS` identity array and its English prose (`meta.title`/`meta.description`/`meta.ogDescription`/`hero.countBold`, plus a doc comment cross-checking the number against `mcp.ts`), duplicated verbatim in `src/copy/tools.<locale>.ts` for all 9 locales; and in `src/copy/index.ts`'s landing-page body copy (+ 9 locale files). The shared chrome (`src/copy/chrome.ts`, `nav()`/`footer()`) no longer carries the count — the redesigned sheet menu dropped the old `toolsSmall` pill — so only after every one of those is updated do `scripts/gen-tools.ts` and `scripts/gen-index.ts` need re-running. If the count ever goes back into `nav()`/`footer()`, all five generators have to re-run on every change (see "Generators" under Public site). Outside the repo, the directory listing names the tools too and needs its own reviewed edit (see "Claude directory listing"). "the registered tool set and every hand-typed tool count agree" in `src/site-copy.test.ts` guards most of it: it scrapes the `server.registerTool("…")` names out of `mcp.ts` (scraped, not imported, since building the server needs Supabase credentials), requires them to equal the names in `TOOLS`, and requires that number in every locale's four `/tools` count fields (`meta.title`/`meta.description`/`meta.ogDescription`/`hero.countBold`), every locale's landing-page `onboarding.toolsCta.body`, and `public/llms.txt`'s "all N MCP tools". It was added after consolidating five settings-`get_*` tools into `get_profile` left stale counts that only a grep caught. `README.md`'s table, the counts in `src/mcp.test.ts` and the directory listing are still checked by hand.

**USDA FoodData Central.** `search_foods` and `get_food_macros` (`src/usda.ts`; the record they normalize into is `src/usda-record.ts`) call USDA with the key from `USDA_API_KEY`, sent only in the `X-Api-Key` header, never in a URL. Quota, the per-user hourly cap and the 429 pause are in-process state per replica (documented in `src/usda.ts`). Fresh `food_cache` rows are served without an upstream call; tests inject fetch and the clock rather than calling the live API.

Every tool declares all five annotation fields; `destructiveHint` is `true` exactly for tools that overwrite or remove a user record (the `delete_*` tools, `delete_account`, `update_meal`, `update_saved_meal`, `update_weight`, `update_body_measurement`, `set_nutrition_goals`), and `openWorldHint` only for `lookup_barcode`, `search_foods` and `get_food_macros` (the USDA tools read an outside database) — "every tool carries directory-ready annotations" in `src/mcp.test.ts` pins both sets. Model-facing text offers writes (`update_meal` backfills, `set_*` preferences) rather than directing them, and never asks for or infers a location the user did not state.

## Claude directory listing

Since 2026-10-01 the server is listed in Anthropic's connectors directory (Community label) at <https://claude.ai/directory/nutrition-mcp>, the URL the landing page's "Add to Claude" button (`CLAUDE_DIRECTORY_URL` in `scripts/gen-index.ts`), the `/alternatives` install steps and FAQ, `README.md` and `llms.txt` link (`scripts/depersonalize.ts` swaps it for a placeholder, since it connects to this server). A listed server must keep meeting the [Software Directory Policy](https://support.claude.com/en/articles/13145358-anthropic-software-directory-policy) and the [review criteria](https://claude.com/docs/connectors/building/review-criteria), and nothing re-checks it: a tool change is never resubmitted, so deploying to `main` is the release, and Anthropic can delist a server that drifts. Every change is held to that bar:

- **Model-facing text describes; it never directs.** Tool descriptions and titles, tool results and `SERVER_INSTRUCTIONS` say what a tool does and when it applies, and must match what it actually does. They never tell Claude how to behave, never steer it toward a tool the user didn't ask for or away from another server's tools, never pull instructions from an external source, never carry hidden or encoded instructions, and never promote anything (no Patreon or other plugs in model-facing text). The approval review flagged "offer …" and "narrate …" phrasing addressed to the assistant even after earlier rounds had softened "direct" to "offer"; fixed in #190.
- **Tool shape.** Names stay ≤64 characters; read and write stay separate tools (no catch-all tool taking a method or action switch); every tool keeps its `title` and annotations, which Claude uses for auto-permissions (read-only tools run without a prompt, destructive ones always prompt) — "every tool carries directory-ready annotations" in `src/mcp.test.ts` pins them.
- **Errors and size.** A failure returns an actionable message, never a bare "Internal Server Error" (`ToolError` / `userFacingError`); inputs are validated, not silently accepted. Responses stay proportional to the request (compact listings, `MEAL_LISTING_MAX_CHARS`, range caps). The listing's health badge counts 5xx responses, timeouts and `isError: true` results against tool calls over 30 days (Healthy is ≤2%, Degraded >5%), visible at [claude.ai/directory/manage](https://claude.ai/directory/manage).
- **Data and scope.** Collect nothing from the conversation beyond what a tool needs, and never ask for Claude's memory, chat history or files. No payments or asset transfers, no AI-generated images, video or audio (the hand-built SVG charts are fine), no ads or sponsored content. OAuth 2.0 over HTTPS and Streamable HTTP stay as they are.
- **Developer obligations.** The privacy policy, terms, support contact (`SECURITY.md` / `security.txt` address), public docs (`/tools` and its troubleshooting section) and the reviewers' test account with sample data must keep working; issues get fixed promptly.
- **Listing edits are separate from deploys.** Tool names shown on the listing are listing metadata, so adding, renaming or removing a tool also needs a listing edit in the dashboard (another item for the tool-count checklist under "Registered tool set"), which a reviewer approves. Three cases. `get_digest` (the nutrition digest, branch `feat/widget-redesign`) is a pre-merge gate: its listing edit must be in place before it reaches `main`, for the same reason. `search_foods` and `get_food_macros` (USDA, `feat/usda-sources`) are a pre-merge gate too: their listing edit must be in place before that branch merges to `main`, because the merge is the release and nothing resubmits the listing. The saved-meal tools `save_meal`, `get_saved_meals`, `log_saved_meal`, `update_saved_meal` and `delete_saved_meal` (#221) are already on `main` and live on prod (since 2026-10-10), so their listing edit is overdue, not a merge gate; check the dashboard now. Whether any of these eight names is on the listing today is not confirmed by the repo, so check the dashboard's tool list against the `server.registerTool()` names before every merge that adds, renames or removes one. Changing the display name requires re-review; the slug is permanent. Anything the dashboard can't edit (e.g. the use-case prompts), and delisting, go to `mcp-review@anthropic.com`.

## Saved meals and meal items

Issue #221. A **saved meal** (`saved_meals`) is a named meal kept with its values for ONE serving and, optionally, its ingredients (`saved_meal_items`); a **logged meal** may carry ingredients too (`meal_items`). Tools: `save_meal`, `get_saved_meals`, `log_saved_meal`, `update_saved_meal`, `delete_saved_meal`, plus an optional `items` list on `log_meal` / `update_meal`; `search_meals` also matches ingredient names and lists matching saved meals. Pure rules live in `src/meal-items.ts`; the migration is `20261010120000_saved_meals.sql` (**apply it to an environment before the code reaches the branch that deploys there** — `deleteAllUserData` deletes from these tables first).

- **The meal's own nutrient columns stay canonical.** When items are given the server sums them (`validateItems`) and refuses caller-sent totals beside them, so every reader — summaries, goals, widgets, Apple Health, export — reads totals exactly as before and never touches the item tables. calories, protein, carbs and fat are needed on every item; fiber, sugar and added sugar go on every item or none (a partial sum would read as a real, too-low figure); alcohol and caffeine are summed over the items that carry them. Sums round to 2 decimals and `assertMealTotals` applies `log_meal`'s per-meal bounds to them. `update_meal` refuses a totals-only change on a meal that has items: its totals change through a full new items list, and the backfill note says so for itemized meals.
- **Writes are atomic through four service-role-only `security definer` functions** (`insert_meal_with_items`, `update_meal_with_items`, `insert_saved_meal`, `update_saved_meal`; `search_path = ''`, executed via `.rpc()`). They trust their input — validation and summing stay in TypeScript, where the tests are, since no test runs SQL. `insertMeal` takes the rpc path only when items or a `saved_meal_id` are given; the importer's plain path is unchanged. Items are not part of the `auto:` idempotency digest: the summed totals already are.
- **Logging a saved meal copies it.** `log_saved_meal` writes an ordinary `meals` row (and copies of the items) with `saved_meal_id` set (`on delete set null`); editing or deleting the saved meal never changes logged meals. `servings` scales first, then `item_amounts` set single items to the amount actually eaten (nutrients scale by new/old amount) and `leave_out` drops items. Stored values are not re-gated by `ADDED_SUGAR_REQUIRED_FROM`; `save_meal` and `update_saved_meal` apply the gate per item like `log_meal`. `save_meal` writes no `meals` row (the landing stats count `meals`). It reuses `MEAL_PROGRESS_OUTPUT_SCHEMA` and the meal-logged widget; the four other new tools declare no `outputSchema`.
- **Names are unique per user ignoring case** (`uniq_saved_meals_user_name`), so a name is a stable handle for `log_saved_meal`; a clash is a `ToolError` naming the existing saved meal.
- **Widgets show a meal's ingredients from `_meta`, never `structuredContent`.** `MEAL_ITEMS_META_KEY` (`"nutrition-mcp.com/meal-items"`, `src/widgets.ts`) carries `{ v: 1, meals: (item[] | null)[] }` aligned by position with `structuredContent.meals`, built by `buildMealItemsMeta` (`src/meal-items.ts`) on `buildMealProgress` (log_meal, update_meal, log_saved_meal), `get_goal_progress` and `get_nutrition_summary` (the kept rows only; added-sugar `extra` rows carry none). The key is omitted when no row has items, item `alcohol_g` is null with alcohol tracking off, and a failed items read drops the key rather than the tool. In the strip's per-metric breakdown (`withMealItems` / `mealList` in `shared/macros.js`) a row with items becomes a disclosure button: one row open at a time, items sorted by the selected metric, "–" for an item without it; rows without items keep their exact markup. Every template repeats the key literal (pinned by tests).
- **Errors quoting the user's own text carry a `logText`.** `ToolError`'s optional `logText` (`toolErrorWithUserText`, `errorLogText` in `src/errors.ts`) is what `withAnalytics` logs in place of the message, so item and saved-meal names reach the caller but never the runtime log. Item refusals use category `meal_items_invalid`.

**Meal types** (`src/meal-types.ts`) are nine values in day order: `breakfast`, `second_breakfast`, `lunch`, `afternoon_snack`, `dinner`, `supper`, `pre_workout`, `post_workout`, `snack`. A type is the meal's place in the user's own day as the user names it, with no clock window attached, so 15:00 can be obiad or podwieczorek. The importer's time-based `inferMealType` still returns only the base four (`BASE_MEAL_TYPES`), and `get_meal_patterns` always lists those four, adding another type only when it appears in the window. The `meals_meal_type_check` and `saved_meals_meal_type_check` constraints must equal `MEAL_TYPES`; `src/meal-types.test.ts` pins both against `supabase/migrations/20261108120000_meal_types.sql`, so a new type needs a migration that re-adds both constraints, 10-locale widget labels for it, and `/tools` copy. Output schemas stay plain strings for `meal_type`, so the widening never touches the frozen schemas.

## Active calories

Issue #220. Energy burned in exercise (typically a watch's "active calories"), logged beside intake. Not a workout tracker: no types, sets or durations, only an optional note. Tools: `log_active_calories`, `get_active_calories`, `delete_active_calories` (`destructiveHint` true, so it is in the destructive set pinned by `src/mcp.test.ts`) and `set_activity_credit` (not destructive, like `set_alcohol_tracking`). Pure rules live in `src/activity.ts`; the table `active_calories_log` and the column `profiles.activity_credit_pct` come from `20261102120000_active_calories.sql` — **apply it to an environment before the code reaches the branch that deploys there** (`deleteAllUserData` deletes from the table first).

- **The calorie goal is never changed by activity.** Net intake (`intake − credited`) and the deficit against the goal are reported beside the goal and nothing else. Activity is never called "earned" food in any text.
- **The credit share is a snapshot.** Each row stores `credit_pct` as it stood when logged (null profile value reads as 100). `set_activity_credit` applies to entries logged from then on; every sum reads the row, never the profile, so changing the preference never rewrites past days. A day's `credited_kcal` is `round(sum(kcal × credit_pct / 100))`, rounded once, not a sum of rounded entries.
- **Reads are silent without activity.** The nutrition summary, goal progress and trends read it only when the period has activity rows; with none, the activity additions are absent, so no activity line or `_meta` key appears. **Activity alone never makes a day logged**: `get_nutrition_summary`'s `logged_days`, its `days` entries and its averages' denominators count meal or water days only, exactly as before active calories existed, so `structuredContent` for an activity-only day is unchanged. Such a day still gets its text section (`## <date> (0 meals)`) and its activity line, and the range's activity line names the activity days. That promise covers **activity only**: the past-day goal change below does change output for a past date with no activity. The `_meta` key is `ACTIVITY_META_KEY` (`"nutrition-mcp.com/activity"`, `src/widgets.ts`), built from per-day totals by `activityMetaFromDays` (`buildActivityMeta` wraps it for raw rows). The summary builds it from the same `activityByDay` map its text uses, so the two cannot drift. It lists days that carry activity only, ascending, and is omitted entirely when there are none. It never goes in `structuredContent`, because output schemas are frozen. Trends sends only the 30-day series the widget re-averages (the text keeps its own window).
- **Net intake is averaged over meal days, not calendar days.** `activityTrendsLine` averages burned and credited over every calendar day of the window, but net intake over only the days with a meal (that day's intake minus that day's credited activity, 0 credited when it had none). Counting an unlogged day as 0 intake minus its credit would pull the average negative. The net clause is omitted when no day in the window has a meal, and the text names both denominators.
- **A past single day is judged against the goal in effect that day (separate from activity).** `get_nutrition_summary` (one day) and `get_goal_progress` resolve their goal through `goalsForDate`: a past date reads goals history (falling back to the current row when no history entry covers that date), read in the same `Promise.all` as the day's rows (`pastDayGoalHistory`), so changing the calorie goal today does not re-judge last week. Today, a future date and every range use the current goal row, as they always have. This changes output for a past single day even when it has no activity.
- **Writes and reads share the water conventions.** Entries go through `resolveWriteTimestamp` like `log_water`; retries dedupe on an `auto:` key over user, kcal, note and resolved `logged_at`, deliberately **not** the credit share (a retry after a preference change is still the same burn). Windows are read through `selectLoggedWindow`. Bounds (kcal 1–10000, share 0–100) are checked in the handler and refused as `ToolError`s, with null on `set_activity_credit` meaning "reset".
- **Export.** `active_calories.csv` carries its own `timezone` column and `credited_kcal`; `profile.csv` ends with `activity_credit_pct`. The archive README and the privacy policy both name the data, so a new column or file updates them together.

### Apple Health activity sync

The opt-in **Nutrition MCP Activity** shortcut (`HEALTH_ACTIVITY_SHORTCUT_NAME`; build guide `docs/apple-health-activity-shortcut.md`) is the one path that READS from Apple Health: it sends its daily Active Energy totals to `POST /api/v1/health-sync/activity`. Pure rules are `src/health-activity-sync.ts`; the migration is `20261103120000_health_activity_sync.sql` (**apply it to an environment before the code reaches the branch that deploys there**: `/start` writes `health_sync_pending.kind`, `deleteAllUserData` deletes `health_activity_links` first, and every activity read selects the new columns).

- **Pairing is the Apple Health flow with a `kind`.** `/start` takes `kind` (`health`, the default, or `activity`; anything else is a 400, so a newer shortcut is never silently paired as the other kind). The pending row keeps it, the callback reopens that kind's shortcut by name (`shortcutRunUrl(code, kind)`), and `/claim` writes that kind's link. The activity link lives in its own table, `health_activity_links` (one per user, same `nmhs_` token shape, hashing and 90/365-day expiry, no lease), so the two shortcuts connect and disconnect independently: `tokenAuth(kinds)` accepts a token only on its own kind's routes, and `/revoke` takes either and removes only that link.
- **A synced day is one row, replaced, never added to.** `active_calories_log.source = 'apple_health'` with `source_date`, unique per user and date, written through the service-role-only `sync_health_active_calories` rpc, which keeps an existing day's `credit_pct` snapshot. `logged_at` is local noon of the date, in the profile timezone (else the phone's). A 0 writes and removes nothing (the shortcut cannot tell "no samples" from "read refused"); only today and the 6 days before are accepted; days are skipped, not refused.
- **On a day with a Health total, hand-logged entries do not count.** `countedActivity` (`src/activity.ts`) drops them before every sum (summary, goal progress, trends, the `log_active_calories` day line); `get_active_calories` still lists them, marked as not added. A watch's Active Energy already includes the workouts someone would log by hand.
- **The copy names the read-back.** The privacy policy and terms (10 locales), the `/apple-health` page's `activity` section (10 locales; its install button is `HEALTH_ACTIVITY_SHORTCUT_URL`, a build-time Dockerfile `ARG` read by `shortcutUrlFromEnv`, "coming soon" while unset) and README describe the today-plus-2-days Active Energy read, the one-entry-per-day replacement and the hand-logged rule; change those rules and the copy changes with them. The localized Health names for Active Energy are AI-chosen and unverified on a device.

## Reads and error text

- **Every `logged_at` window read goes through `selectLoggedWindow` (`src/supabase.ts`).** `getMealsInRange` / `getWaterInRange` / `getWeightInRange` / `getBodyMeasurementsInRange` page with `.range()`, order by `logged_at` then `id`, drop the adjacent duplicate a backdated insert between pages can produce, and reconcile the deduped length against the first page's exact count, throwing `result would be truncated` (category `read_truncated`) when short. The three `get*ByDate` readers delegate to them. The `id` tie-break is load-bearing: date-only imports all anchor at local noon, so ties at a page edge are routine. An unpaged select kept PostgREST's _oldest_ 1000 rows, so a 365-day `get_trends` showed the latest 30 days as zeros. The range caps (`MEALS_RANGE_MAX_DAYS` 31, `SUMMARY_RANGE_MAX_DAYS` 92, `WEIGHT_RANGE_MAX_DAYS` 366, `BODY_MEASUREMENT_RANGE_MAX_DAYS` 366) are about response size, not truncation. `getBodyMeasurementsInRange` takes an optional `kind`, applied in the database (`selectLoggedWindow`'s `filter`), so the exact count covers the filtered set rather than the whole window.
- **Meal listings render through `renderMealListing` (`src/meal-listing.ts`).** `get_meals_today`, `get_meals_by_date` and `get_meals_by_date_range` take `detail: "compact" | "full"`, default `"compact"`: one line per meal — local `HH:MM`, type, description (clipped at 200 characters), calories and non-null nutrients (alcohol gated exactly like `formatMeal`, since the opt-in exists for users in recovery), a `notes` flag in place of the note text, and `[id: …]`, which `update_meal`/`delete_meal` need. `"full"` is the old per-field block, including notes, and never clips. Both name the profile timezone once (`Times are local (…).`) and print local time by slicing `formatLocalDateTime` — never a raw UTC ISO string, which filed a Kyiv user's 21:00 dinner at 19:00Z. Output is capped at `MEAL_LISTING_MAX_CHARS` (40_000): whole days are added while they fit, a meal boundary is only the fallback when the first day alone overflows (at least one meal is always shown), and a truncated listing ends with a notice naming the concrete continuation call. The module is pure — it must never import `mcp.ts` or Supabase. Water and weight listings get local time and the timezone header too, but no `detail` param and no budget (weight is at most 366 short lines). Body-measurement listings (`get_body_measurements`) get local time, the timezone header and the `MEAL_LISTING_MAX_CHARS` whole-day budget: the first day is always shown, and a truncated listing names the date to continue from. `get_nutrition_summary`'s `structuredContent.meals` is not every meal: `topMealBreakdown` sends the order-preserving union of each metric's top `MEAL_BREAKDOWN_TOP_N` (at most 64 rows; added sugar deliberately does not rank rows, so `structuredContent.meals` is unchanged with or without `_meta` — its list draws from the kept rows that carry a value plus `_meta`'s `extra`, see below) — fewer rows, so it still validates under the unchanged schema. The per-metric count of meals with a value above zero travels in the result's **`_meta`** under `MEAL_CONTRIBUTORS_META_KEY` (`"nutrition-mcp.com/meal-contributors"`), on both return paths, and the widget's "N more meals" line is `contributors − shown`. It is not a `structuredContent` field because output schemas are frozen (see "Server wiring" above): shipping it there as `meal_contributors` failed every summary call on dev for hosts still holding the old tool list. `shared/bridge.js` hands the result's `_meta` to `render` as its second argument. A host that drops it leaves the new widget on hedged wording rather than a number it cannot know: "+ N or more" past 8 rows, "+ possibly more" at exactly 8 (the commonest trim, where one set of big meals leads every metric), and an exact count only when `sum(days[].meal_count)` shows the server trimmed nothing. One known transitional miscount remains: a host still running the pre-change widget HTML from its cache (the `ui://` URI is unchanged) computes `rows − 8` against the now-bounded `meals` and undercounts "N more" until it refetches the resource — the payload still validates, only that line is low. The summary widget repeats `MEAL_CONTRIBUTORS_META_KEY` as a literal (it cannot import), so `src/mcp.test.ts` asserts the assembled widget contains it; the harness imports it from `src/widgets.ts`, where it is defined. `MEAL_BREAKDOWN_TOP_N` (defined in `src/widgets.ts` so the harness can import it, re-exported from `mcp.ts`) must equal `CAP` and the `extra` cap in `public/widgets/src/shared/macros.js`; `public/widgets/macros.test.ts` checks both, since a mismatch makes the widget's list and its "more" count disagree. **Added sugar never enters `structuredContent`** (the schemas are frozen): `log_meal`, `update_meal`, `get_goal_progress`, `get_nutrition_summary` and `get_trends` carry it in `_meta` under `ADDED_SUGAR_META_KEY` (`"nutrition-mcp.com/added-sugar"`, `src/widgets.ts`), built by `buildAddedSugarMeta` (`src/added-sugar.ts`) as `{ v: 1, goal, days, meals, contributors?, extra? }`. `extra` is `get_nutrition_summary`'s alone (the single-day tools list every meal of the day, `get_trends` has no list): `addedSugarExtra` ranks every meal in the range by added sugar (one decimal, > 0, ties to the earlier meal — topMealBreakdown's rule), takes the top `MEAL_BREAKDOWN_TOP_N` and sends those not among the kept rows, as `{ description, meal_type, date, added_sugar_g }` built from `mealBreakdown`'s own row. Without it a 30 g sweetened drink that tops no other metric was missing from the added-sugar list while `contributors` counted it. The widget validates `extra` as untrusted (an array; each entry rebuilt from those four fields, kept only with a string description and a finite positive `added_sugar_g`; at most 8), drops it entirely when the position join of `meals` fails, and adds the rest to the added-sugar cell's list only (`metricRows`), so every other metric's list and count is untouched, "+N more" stays `contributors − shown`, and with no `extra` it renders exactly as before. Optional and additive, so `v` stays 1. `days` is null for a day with no recorded value (never 0), and `meals` (keyed by meal id) is built from exactly the meals behind the rows the tool returns, in row order, because the rows carry no id and `withAddedSugar` in `shared/macros.js` matches them by position (and only when the counts agree). Without the payload the strip is byte-for-byte the four-limit one. Every template repeats the key as a literal, asserted by `src/mcp.test.ts` and `public/widgets/macros.test.ts`.
- **A set added-sugar limit with nothing recorded is stated, never dropped.** `addedSugarNotRecorded` (`src/insights.ts`) is the one wording — `not recorded on this day (limit 29g)` in `formatProgress` (log_meal, update_meal, get_goal_progress, each summary day), `not recorded in this period (limit 29g)` in the summary's average line, `computeTrends` and `computeWeeklyDigest` — gated on an active ceiling (0 included). Dropping the line let a model read total sugar against the added-sugar limit (a cola logged with `sugar_g` 35 and no `added_sugar_g`). Without a limit the output is unchanged, and partial coverage keeps the days-with-data notes. Every `AddedSugarMeta` carries `goal` on every return path, so the widgets can show the same gap.
- **`sugar_g` without `added_sugar_g` is refused once `ADDED_SUGAR_REQUIRED_FROM` has passed.** `log_meal` refuses any call giving `sugar_g` (0 included) with no `added_sugar_g`; `update_meal` only when it gives `sugar_g` without `added_sugar_g` and the stored meal's `added_sugar_g` is null. Checked before any write (for `update_meal`, after the stored-sugar read), as a `ToolError` carrying its own analytics category, `added_sugar_missing` (`addedSugarMissingError` in `src/added-sugar.ts`; `ToolError`'s optional `category` beats `categorizeError`'s wording tiers). `bulk_import_meals` and the import widget never apply it — third-party exports rarely carry added sugar. The env var is an ISO-8601 date or offset date-time, read per call by `addedSugarRequiredNow()` in `src/mcp.ts` (tests set and restore `process.env`, no `mock.module`); unset, empty or unparseable is off, and a bad value logs one `[config]` warning at startup. The gate exists because hosts cache `tools/list` for days: a client still on a list from before `added_sugar_g` cannot send the field, so enforcing early fails every sugared meal those users log, each an `isError` result against the directory health badge — set it well after the deploy that advertised the field. The field descriptions and `NUTRIENT_COVERAGE` say a call "may be refused", which is true with the gate on or off.
- **`ToolError` (`src/errors.ts`) is the only error text that reaches the model.** `withAnalytics` returns a `ToolError`'s message verbatim; every other error becomes a per-category message (`userFacingError` in `src/analytics.ts`) plus an 8-hex `ref` from `newErrorRef()`, and the raw message is logged JSON-escaped under that ref with no user id. The weekly-summary resource, the import's per-row `insert_failed` and `lookup_barcode`'s Open Food Facts fallback follow the same rule outside `withAnalytics`. Throw `ToolError` only for text written for the caller, never to wrap third-party text. `csv.ts` / `chunk.ts` are `@inlinets`-inlined into widgets and must not import it.
- **Sodium** (`sodium_mg`, milligrams of sodium, not salt, on meals, meal items, saved meals and saved-meal items; `daily_sodium_mg` ceiling on goals and goals history; `20261024120000_sodium.sql`). **Apply that migration to an environment before the code reaches the branch that deploys there** (dev before `dev`, production before `main`, `db push --dry-run` first): `insertMeal`, the item payloads, `upsertNutritionGoals` and the update snapshot guards always send or filter on the new columns, and the four rpc functions are re-created to read them, so without it every meal write, import row, saved-meal write and `set_nutrition_goals` fails on an unknown column. The tools attach `buildSodiumMeta` (`src/sodium.ts`) under `SODIUM_META_KEY` (`"nutrition-mcp.com/sodium"`); meal-logged, nutrition-summary and goal-progress read it for their sodium row (`withSodium` and `withItemSodium` in `shared/macros.js`, the same position join as `withSaturatedFat`), the trends widget reads its per-day series (a sodium chip, chart and card, its literal pinned by `src/mcp.test.ts`), while the macro strip the other widgets draw (`shared/macros.js`) still has no sodium cell. The import widget does map and preview sodium.
- **Body measurements** (`body_measurement_log`, `20261002120000_body_measurements.sql`; tools `log_body_measurement`, `get_body_measurements`, `update_body_measurement`, `delete_body_measurement`, `set_length_unit`). A row stores the canonical integer `value_mm` plus `value_entered` and `entered_unit` exactly as typed, so a display in the entry's own unit shows the user's number back rather than a round-tripped one. The write unit is the explicit `unit`, then the saved `profiles.preferred_length_unit` (nullable, no default), then a refusal (`pickLengthWriteUnit` in `src/units.ts`); the weight unit is never consulted. `update_body_measurement` defaults to the unit the entry was recorded in. `PLAUSIBLE_LENGTH_MM` is a set of per-site typo guards (mm typed as cm, an extra digit, a cm/in swap at the extremes) whose refusal adds an other-unit hint only when the same number would be plausible in the other unit — not health bands, and it cannot catch a cm/in swap inside the overlap (`upper_arm` 12–39.4 is valid in both). `BODY_MEASUREMENT_KINDS` must equal the migration's `body_measurement_log_kind_check` list (pinned by `src/units.test.ts`); adding a kind needs a migration that drops and re-adds that constraint. One value per site: there is no side column, a left/right goes in notes. `bodyMeasurementIdempotencyKey` hashes `kind` (so waist 80 cm and hips 80 cm at the same instant stay two rows) and `value_mm` (so 80 cm and 31.5 in are one), and its field list is positional, so it is frozen once shipped; notes are decoded before hashing, unlike weight and water (#79). The landing-page stats deliberately exclude measurements. The tools declare no `outputSchema` (null entries in `src/output-schemas.frozen.json`).
