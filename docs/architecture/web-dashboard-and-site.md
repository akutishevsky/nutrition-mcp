# Web Dashboard & Public Site

## Web dashboard

A signed-in, **read-only** view of the user's own data at `/dashboard` (English) and `/{locale}/dashboard`. The migration is `20261109120000_dashboard_sessions.sql` — **apply it to an environment before the code reaches the branch that deploys there** (dev before `dev`, production before `main`): `deleteAllUserData` deletes `dashboard_sessions` first, and the hourly sweep and every page load query it, so without the table account deletion fails and every dashboard visit answers `unavailable`.

- **Pages.** `scripts/gen-dashboard.ts` renders `public/dashboard.html` and every locale's from `src/copy/dashboard.ts` (`DashboardDoc`, one `dashboard.<locale>.ts` per locale, inlined into the page as `<script type="application/json" id="dash-strings">`); `public/dashboard.js` is the client. The HTML is a static shell with no user data; tabs Today / History / Trends / Body are client-side views keyed by the URL hash (`#today` default). They are `APP_PAGE_ROUTES` in `src/routes.ts`, **not** `PAGE_ROUTES`: no sitemap, no hreflang set, `noindex, nofollow` in the meta tag and the `X-Robots-Tag` header. **No analytics**: `BASE_HEAD_ASSETS` and `consent: false` on `nav()`/`footer()`, like login, so the privacy policy can say no tracker runs there. `nav(…, { app: "dashboard" })` swaps the marketing links for the four tabs and a **Sign out** form. Every other page `nav()` renders (landing, `/tools`, legal, alternatives, apple-health, login) links to its own locale's dashboard twice: a secondary `.head-dash` pill just before Connect (icon-only below 1060px, label kept as its accessible name) and a `.menu-dash` button beside GitHub in the sheet menu, labelled `ChromeCopy.dashboardCta`, which uses the same word as that locale's dashboard page title; the dashboard pages themselves carry neither. The landing page also has a `#dashboard` section right after the examples (`renderDashboard` in `scripts/gen-index.ts`, copy in `IndexDoc.dashboard`, styles in `scripts/landing-css.ts`): a heading, four cards for the four tabs, and a button to the locale's dashboard. For search, its FAQ entry is spliced into the visible FAQ and the FAQPage JSON-LD after the saved-meals entry (`faqEntries`; its answer links with `data-link="dashboard"`, which `localizeLinks` rewrites per locale), its `featureListItem` is appended to the SoftwareApplication `featureList`, and its `keywords` to the meta keywords. `public/llms.txt` describes the dashboard too. `src/alt-pages.test.ts` and `src/site-copy.test.ts` pin both; since the header link is in the shared chrome, changing it means re-running every `nav()` generator. The signed-in page shell is read from disk once per locale (`createAppPageHandler`) and served from memory with an ETag under `Cache-Control: private, no-cache`; the session check runs on every request before `If-None-Match` can earn a 304, so a signed-out browser is always redirected, and the 302/429/503 stay `private, no-store`. A signed-out visit is 302'd server-side to `/dashboard/login?locale=xx`; when the session store cannot answer, `readDashboardUserId` throws `DashboardSessionUnavailableError` and the page answers 503 instead, because an outage is not a sign-out (the API's `dashboardSession` middleware answers 503 `unavailable` for the same reason).
- **Sign-in reuses `/authorize`.** `/dashboard/login` starts an OAuth flow as the first-party in-memory client `DASHBOARD_CLIENT_ID` (`nutrition-mcp-dashboard`, `src/dashboard-client.ts`), resolved by `withFirstPartyClients` exactly like `HEALTH_SYNC_CLIENT`: never a row in `oauth_clients`, its only redirect is this server's own `/dashboard/callback` byte for byte, and `/token` refuses it. So password, Google, the binding cookie and the consent notice (a dashboard heading variant, chosen only for this client id) are the hardened ones, not a second login. A started sign-in holds **no server state**: the per-flow start cookie (`nm_dash_start_<16 hex of sha256(state)>`, HttpOnly, 10 minutes) carries `<PKCE verifier>.<locale>.<expiry ms>`, and the flow's `state` is `hashSecret("dashboard-state:" + value)`, so the callback rebuilds the flow from the cookie and checks it against the state. An in-memory map used to hold it, and a flood of starts from rotated `x-forwarded-for` values could evict real users' flows; no secret seals the cookie because whoever could forge a value could as well start a real flow. A callback arriving without the matching cookie (another browser, or one already dropped at expiry) or after expiry **spends its code** before refusing, so a code that reached the wrong browser cannot be carried to the one holding the cookie. The privacy policy (10 locales) says what that cookie holds. `/dashboard/callback` redeems the code from the store (`consumeAuthCode`, client id, exact `redirect_uri`, `verifierMatchesChallenge`), sets the session cookie and 303s to the locale's dashboard. The login page's dashboard heading is swapped in at render time by `renderLoginPage` (`LOGIN_DASHBOARD` in `src/copy/login.ts`), so the generated login template is unchanged. `/dashboard/login`, `/dashboard/callback` and `/dashboard/logout` are throttled by `rateLimitAuth` inside the dashboard router (`DASHBOARD_AUTH_PATHS`), not via `OAUTH_PATHS`, so a request is never counted twice.
- **Session.** Cookie `__Host-nm_dash` over https, bare `nm_dash` on plain-http dev (the binding cookie's rule), `HttpOnly; SameSite=Lax; Path=/`. Value `nmds_` + `newOpaqueToken()`, stored only as `hashSecret(raw)` in `dashboard_sessions` (RLS on, no policy, service_role only). Idle expiry 7 days, slid at most hourly; absolute expiry 30 days. Swept on the hourly `startOAuthCleanup` tick. `authenticateBearer` refuses an `nmds_` Bearer at `/mcp` with a 401 and a strike before any lookup, as it does `nmhs_`; the dashboard never accepts a Bearer. The privacy policy (10 locales) names the cookie, its hash-only storage, the 7/30-day lifetimes, sign-out, deletion and the export row, and `src/site-copy.test.ts` pins the cookie name and the dashboard URL in every locale — change any of those and the copy changes with it.
- **CSRF.** Sign-out is `POST /dashboard/logout`, accepted only when the request is same-origin **and** the body's `csrf` equals the derived value. Same-origin is `Origin` equal to the site origin, or `Origin: null` with `Sec-Fetch-Site: same-origin`; the dashboard pages also send `Referrer-Policy: same-origin` (the site's `no-referrer` makes browsers send `Origin: null` on a form post, which broke Sign out in every real browser while tests sending a real Origin passed), and the security-headers middleware only sets `no-referrer` when a route has not chosen its own. The session ends only once its row is deleted: if that fails the cookie stays and a 503 page (`DashboardDoc.signOutFailed`) offers the form again, since the legal copy says signing out ends it at once. A same-origin form post with a stale or missing `csrf` (a tab left open across a sign-in in another tab) gets the same page with 403 and a fresh `csrf` derived from the current cookie, when that session is still live (gone: cookie cleared, 303 to the landing page; store down: 503; throttled: 429 with `Retry-After`); JSON callers keep the JSON 403, and a cross-origin post is refused before any page is built. `GET /api/dashboard/session`'s 503 for a failed profile read still carries `csrf` (it needs only the cookie), and `dashboard.js` refetches it when Sign out is pressed without one. That value is never stored: `hashSecret("dashboard-csrf:" + rawCookieToken)`, compared with `timingSafeEqual`, handed to the page by `GET /api/dashboard/session`. The Sign out form also posts `locale`, so sign-out lands on that locale's landing page. It is stable across tabs and unknowable without the httpOnly cookie. Every other dashboard route is a GET that reads.
- **Data path.** `/api/dashboard/*` is cookie-only JSON with `Cache-Control: private, no-store`, outside the global CORS middleware (`isDashboardPath`), on its own per-user rate-limit bucket (`DASHBOARD_LIMIT_PER_WINDOW`, 120/min; `GET /api/dashboard/session` included, though it lives in the auth router). Before that, each cookie lookup is reserved before its database read against a per-IP budget (`DASHBOARD_LOOKUP_FAILURE_LIMIT`, 30/min) and a process-wide one (`DASHBOARD_LOOKUP_FAILURE_GLOBAL_LIMIT`, 300/min, which bounds the reads whatever `x-forwarded-for` says) through `reserveDashboardLookup` in `src/rate-limit.ts`, and handed back by `refundDashboardLookup` unless it finds no session (a valid session or an unavailable store refunds), so a concurrent burst cannot overrun either budget. Past either one, a lookup (API, session endpoint, page routes) answers 429 before the read, unless this process has seen that session valid (`DashboardSessionCache` in `src/dashboard-auth.ts`, keyed by `hashSecret(token)`, bounded, filled by every successful lookup and every session `/dashboard/callback` creates, never trusted past the row's own cached expiries, dropped on this process's logout). Such a session passes with no read within `DASHBOARD_SESSION_CACHE_TTL_MS` (60 s) of its last validation, and after that through one read outside the budget that refreshes it (`noteDashboardLookupFailure` counts it if the row is gone), so a flood never signs out a dashboard in use or loops a fresh sign-in. A forged cookie is never in the cache. The cache is consulted only during a throttle, so outside one nothing changes; inside one, a sign-out on another replica takes up to the TTL to reach this one. Only failed lookups stay counted, and they are deliberately **not** auth strikes: a strike feeds the per-IP ban that also sheds `/mcp`, and an expired dashboard cookie must not do that. A no-meta `isError` from the in-process call is `bad_request` only when its text is the SDK's input refusal (`Input validation error:` / `Invalid arguments for tool`); anything else (an output-schema failure) is `server_error` under a fresh ref, and a failure building the server (its profile read) is `unavailable`. Every handler catches everything and answers `{ ok:false, error, message, ref? }` from the fixed vocabulary `unauthenticated` / `bad_request` / `rate_limited` / `unavailable` / `server_error`, with exactly one `[dashboard] route=<name> result=<code>` line per call — never a user id, email, date or query text. Widget payloads come from running the **real registered tool** in-process (`runDashboardTool`: the exported `buildMcpServer(baseUrl, userId, undefined, "dashboard", DASHBOARD_REGISTRATION)` and a v2 `Client` over `InMemoryTransport`, both closed in `finally`; `DASHBOARD_REGISTRATION` is a `RegistrationFilter` (`src/mcp.ts`), so each in-process call registers only the five dashboard tools and their widget resources, while `/mcp` passes no filter and registers all 53 — the `server.registerTool("…")` calls themselves are unchanged, so the tool-count scrape still sees every name; `surface` is a build-time argument that `registerTools` closes into the analytics context, not an `authInfo` field), returning `{ structuredContent, _meta }`, never `content`; only `get_nutrition_summary`, `get_goal_progress`, `get_trends`, `get_weight_trends` and `get_digest` are allowed. **With `surface === "dashboard"`, `withAnalytics` writes no `tool_analytics` row and prints no `[analytics]` line**: a dashboard read is not a tool call and must not move the directory health stats or the legacy-era count, and the privacy policy promises it writes no telemetry. A failing dashboard call instead logs one `[dashboard] tool-error tool=… error=<category> ref=…` line and puts `{category, ref, toolError}` in the result's `_meta` under `DASHBOARD_ERROR_META_KEY`, which the route maps to its error code; that key only exists on the in-process path, no MCP client ever sees it. Calendar, search, saved meals, body measurements and status are plain JSON from `supabase.ts` readers (`src/dashboard-api.ts`). Read-only is a promise in the legal copy: a write route here needs the policy and terms changed first.
- **Widget iframes and the host shim.** Each card is a `sandbox="allow-scripts"` iframe (no `allow-same-origin`) on `/dashboard/widget/:key` (`nutrition-summary`, `goal-progress`, `trends`, `weight-trends`, `digest`), serving `getWidgetHtml(key)` without auth under its own CSP (`default-src 'none'`, inline script and style, `img-src data:`) with `frame-ancestors 'self'` and no `X-Frame-Options: DENY` — the one route the site lets a page frame, and only a response that carries `WIDGET_CSP` with a status below 400 (the 200 and its 304; `isFrameableWidgetResponse` in `src/index.ts`) is exempt, so the route's 404/500 get DENY and the site CSP; the dashboard page's CSP gains `frame-src 'self'`. `public/dashboard.js` is an MCP Apps host modelled on `scripts/widget-harness.ts`: answer `ui/initialize` with `hostContext { theme, locale, displayMode: "inline" }`, wait for `ui/notifications/initialized`, then send `ui/notifications/tool-result`; grow on `size-changed` from a 130px start; accept a message only when `event.source === iframe.contentWindow`; send `host-context-changed` when the site theme changes; answer app `tools/call` only for the allowlisted tools through `/api/dashboard/tool/:name`, a JSON-RPC error for anything else. The bridge invariants under "Custom UI Widgets" hold here too. The one widget-side difference is keyed on the host name dashboard.js announces (`hostInfo.name` `"nutrition-mcp-dashboard"`, `DASHBOARD_HOST_NAME` in `shared/bridge.js`, both literals pinned by `src/dashboard-api.test.ts`): no chat-only settings footer, and `html.host-framed`, under which `shared/base.css` drops a root `.panel`'s own card and the root's gutter and width cap so the page's card is the only surface. dashboard.js treats every `ui/initialize` as a new handshake (`ready` false until `initialized`), and keeps a view's content mounted across refreshes and Today date steps (dimmed via `aria-busy`), so frames are not detached and reloaded.
- **Nothing model-facing changes.** No new MCP tool, no tool text or `outputSchema` change; the tool count and `src/output-schemas.frozen.json` are untouched by the dashboard.

## Public site (`public/*.html`)

One design system, soft, rounded and glassy: neutral blue-grey surfaces with a green accent, big radii (20–32px), a header of two floating glass pills, three blurred colour blobs drifting behind the top of each page (`blobs()`, emitted by `nav()`), and the in-chat widgets' nutrient palette (`--cal --pro --car --fat --wat --fib --sug --caf`). Type is Urbanist (500–800) for all text and Geist Mono for codes, counts and labels, from Google Fonts; Urbanist is Latin-only, so `/uk` adds Mulish after it (`localeFontLinks()` in `scripts/site-partials.ts`, chained in the `html[lang]` `--font` overrides) and `/ja` downloads nothing extra: its override falls through to system Japanese fonts (Hiragino, Yu Gothic, Meiryo, Noto CJK) — M PLUS 2 was dropped as ~1 MB per page. The CSP already allows Google Fonts.

- **`public/styles.css`** holds only what every page shares, in numbered sections: tokens on `body` (every dark value is declared once in the `prefers-color-scheme` block and once in `body[data-theme="dark"]`, so a new colour must be added to all three blocks), keyframes, base + reveals, blobs, header, sheet menu, footer, consent banner, and the `.nm-*` primitives pages are built from (`.nm-container`, `.nm-card`, `.nm-btn-*`, `.nm-chip`, `.nm-faq-row`, …). Nothing in it is scoped to a single page: page layout goes in that page's generator as an inline `<style>` (the landing page's in `scripts/landing-css.ts`) built from the tokens and primitives — never a hardcoded light-only colour. The pre-redesign "Nutrition Facts" stylesheet and its token aliases (`--rule`, `--accent`, `--surface`, …) are gone; do not reintroduce them.
- **`public/site.js`** (served at `/site.js`, loaded with `defer` by every page) owns the three-state theme control (every `[data-theme-set]` button, synced via `aria-pressed`, plus `<meta name="theme-color">`), the analytics consent banner and "Cookie settings" reopen (a no-op when `window.nmConsent` is absent, as on login and NOINDEX builds), the mobile sheet menu (focus trap, Escape, `inert` on everything outside, scroll lock, auto-close once the hamburger is hidden), the nav fit check (from 1060px, an overflowing nav first sets `html.head-compact`, which drops the Dashboard pill to its icon, and only if it still overflows also sets `html.nav-tight`, which hands the page to the hamburger while the pill stays icon-only, so its label never reappears as the window narrows) and its sliding active indicator, same-page scroll-spy, the language `<details>` light-dismiss, `[data-reveal]` / `[data-reveal="stagger"]` entrance reveals, the `.copy-mini` buttons, the live-stats nav badge and the `[data-gh-stars]` counts. Reveals only hide content once `html.js` is set, so the pages are complete without script. Every effect is off under `prefers-reduced-motion`.
- **The header + menu markup is shared**, not hand-copied: `scripts/site-partials.ts` exports `nav(locale, suffix, currentSuffix?)` and `footer(locale, currentSuffix?)`, used by every generator — `scripts/gen-index.ts`, `scripts/gen-tools.ts`, `scripts/gen-legal.ts`, `scripts/gen-alternatives.ts`, `scripts/gen-apple-health.ts`, and `scripts/gen-login.ts`. Every public page is generator-driven now (the landing page and `/tools` were the last two hand-authored files; both moved onto `gen-index.ts`/`gen-tools.ts`) — `public/login.html` is the one page that's a genuinely different case, since its generated output is a runtime _template_ rather than a finished page (see below). When the nav changes, change `site-partials.ts` and re-run every `scripts/gen-*.ts` — see the shared-chrome-data note under "Generators" below for why a generator whose own data file didn't change still needs re-running.
- **Analytics tags live in `scripts/site-partials.ts`, not in any generator, and nothing loads before consent.** `HEAD_ASSETS` is `STYLE_ASSETS` (fonts, icons, styles) plus `analyticsHead()` when `ANALYTICS_ENABLED`: one inline `<script data-analytics>` that sets basic Consent Mode v2 defaults (all four signals `denied`) and exposes `window.nmConsent.load()`, which alone injects gtag.js (`GA_MEASUREMENT_ID`, Google signals off, `cookie_expires` matching the choice) and Microsoft Clarity (`CLARITY_PROJECT_ID`, then `consentv2`); only `analytics_storage` is ever granted, the `ad_*` signals stay denied. The choice is `{v:1, choice, at}` in localStorage `consent`, valid for `CONSENT_MAX_AGE_DAYS` (182, ~6 months); with nothing valid stored, a Global Privacy Control signal counts as denied. The consent banner is a strip `nav()` renders in the normal flow between the skip link and the sticky header — it pushes the page down rather than covering it, and since `data-consent` is stamped in `<head>` before first paint nothing shifts; reopened from the "Cookie settings" button `footer()` renders, it docks to the bottom edge (`html[data-consent-reopen]`). The logic — clicks, withdrawal (consent update, `clarity("consent", false)`, reload) and deleting `_ga`/`_ga_*`/`_clck`/`_clsk` on any denial — is in `public/site.js`. **Login has no analytics at all**: `gen-login.ts` takes the analytics-free `BASE_HEAD_ASSETS` and passes `{ consent: false }` to both `nav()` and `footer()`. `NOINDEX` (`ANALYTICS_ENABLED` false) drops the snippet, banner and button together. `scripts/depersonalize.ts` (which must leave none of the maintainer's personal info — name, email, GitHub/Patreon/Medium/YouTube links — on any page, in any locale; its closing guard exits 1 on residue under `public/`) strips all three by their `data-analytics` / `consent` markup and requires each on every page but login, so a `⚠ 0×` means the markup changed. A new tracker must be injected inside `load()`, never as a static tag, and adding or removing one still touches the CSP in `src/index.ts` (Clarity needs `https://*.clarity.ms` in `script-src`/`connect-src`/`img-src` and `https://c.bing.com` in the last two), the privacy policy and terms in all ten `src/copy/legal*.ts` locales, and `scripts/depersonalize.ts`.
- **GitHub star counts are fetched server-side only.** `GET /api/github-stars` (`src/github-stars.ts`) calls the GitHub API with no visitor data, caches a good count for an hour and a failure for 5 minutes (GitHub allows 60 unauthenticated calls an hour), and `public/site.js` fills every `[data-gh-stars]` badge from it, revealing a badge only once a number arrives. No visitor request reaches GitHub, so `api.github.com` is not in the CSP and the privacy policy (all 10 locales) says so; every GitHub button shows the count except the header nav icon.
- Keep the pre-paint `<script>` right after `<body>` that applies the saved `theme` from localStorage — it is what prevents the light flash on dark-mode visitors.
- **Every request passes through Cloudflare**, DigitalOcean's managed instance in front of the app, with no dashboard of our own. Its Email Obfuscation is on and cannot be switched off: it rewrites every `mailto:` and bare address in served HTML to a script-only `/cdn-cgi/l/email-protection#…` link. So every generator wraps its whole `<body>` contents in one `<!--email_off-->` … `<!--/email_off-->` pair — `EMAIL_OFF_OPEN` just before `THEME_PREPAINT`, `EMAIL_OFF_CLOSE` just after `SITE_SCRIPT` (`scripts/site-partials.ts`) — and `src/alt-pages.test.ts` pins exactly one pair per generated page with every address inside it. A new generator or a second `<body>` template needs both. `depersonalize.ts` leaves the comments in place.
- **The landing page's world map is k-anonymous: a timezone is named only once at least `TZ_MIN_PROFILES` (3) profiles use it** — the privacy policy promises it. `public_landing_stats()` filters `timezone_list` / `timezone_counts` with `having count(*) >= 3` (`20260929130000_landing_stats_k_anonymity.sql`), and `publicLandingStats()` in `src/supabase.ts` applies the threshold again, so either side deploying first is safe; with no counts it serves an empty list, never an unfiltered one. Exact counts never leave the process (`timezoneLevels()` buckets them, as shares of the published timezones only). The single `timezones` number still counts every distinct timezone — it names none.

### Internationalization (i18n)

The site is being translated into German, Spanish, French, Dutch, Polish, Italian, Ukrainian, Japanese and Turkish (`LOCALES` in `src/routes.ts`) — deliberately not Russian. English stays unprefixed at `/`; every other locale lives under `/{locale}/...` with identical slugs (`/de/tools`, `/de/myfitnesspal-mcp` — slugs are never localized, only content). `src/routes.ts` is the single source of truth for locale/route data (`LOCALES`, `PAGE_ROUTES`, `ALT_PAGES`, `pathFor`/`urlFor`/`hashPath` helpers) — it has no Supabase or other side-effecting imports, unlike `src/index.ts`, so it's safe to `import` directly from generators and tests instead of regex-scraping source text (`src/alt-pages.test.ts` used to have to do that; it doesn't anymore).

**Content model**: every page type is generated, in every locale including English, from typed TypeScript data — never hand-authored HTML sitting next to generated translations. Each namespace's master schema and canonical English copy live in `src/copy/<name>.ts` (`chrome.ts`, `dashboard.ts`, `index.ts`, `tools.ts`, `widgets.ts`, `legal.ts`, `login.ts`, `alternatives.ts`, `alt-ui.ts`, `apple-health.ts`, `health-sync.ts`). All non-English translations (`de`/`es`/`fr`/`nl`/`pl`/`it`/`uk`/`ja`/`tr`) live as sparse, keyed JSON overlays in `src/copy/translations/<locale>.json` (loaded via `src/copy/translations.ts` and merged onto English by `src/copy/merge.ts`). Keys identical to English and structural fields (e.g. `index`'s `hero.chat.exchanges` and `examples.slides` metadata) are omitted from the JSON overlays, and missing keys automatically fall back to English — so editing English never breaks `bun run typecheck` across 9 locale files, while one JSON file per locale keeps translation diffs isolated. For widgets, `WIDGET_STRINGS_COMPACT` (`src/copy/widgets.ts`) inlines only English plus per-locale diffs into the assembled HTML, and `public/widgets/src/shared/i18n.js` merges the active locale onto `en` at render time (setting `WIDGET_ENGLISH_ONLY=1` omits non-English overlays in English-only self-hosted builds).

**The header nav, mobile menu, and footer are shared by every generator** (`nav()`/`footer()` in `scripts/site-partials.ts`) and were the one piece of chrome nobody translated: every HREF was already locale-aware (`pathFor`/`hashPath`), but every visible label was a hardcoded English string, so a fully-translated page still had an English menu bar and footer framing it on every locale. `src/copy/chrome.ts` (`ChromeCopy`) fixes this the same way as everything else — one file per locale, merged into `CHROME_COPY`, read via `chromeFor(locale)` inside `nav()`/`footer()`. A 7-locale native-level proofreading pass (one agent per locale, reviewing the actual rendered HTML, not the source data) is what caught this, along with several smaller gaps worth knowing about since they're easy to reintroduce: a translatable field added to an existing `*Doc` interface only helps once every generator call site that used to hardcode that string is updated to read from it (`ToolsDoc.ui`'s `parametersLabel`/`requiredLabel`/`optionalLabel`/`trySayingLabel` fixed the same class of bug on `/tools`, where those 4 labels repeated ~20–40× per page); a raw-HTML field's aria-label needs translating too, not just its visible text (`AltUiCopy.app.copyUrlAriaLabel`); and a UI element that looks like a proper noun ("Claude"/"ChatGPT" tabs) can sit right next to one that isn't (`IndexDoc.install.otherTabLabel`, the "Other agents" tab) — both need the same review, not just the obvious one.

**The `/alternatives` pages split translatable content into three layers, not one** — a lesson learned from shipping the first two without the third and getting half-translated pages: `src/copy/alternatives.ts`'s `AppCopy` (keyed by app slug) is the prose that genuinely differs per app — hub blurb, cons, the "moving from X" and "bring your history" sections, per-app FAQ extras; `AltPageMeta` in the same file is the `<title>`/description/`og:description` templates (an `{app}` placeholder standing in for the untranslated brand name); and `src/copy/alt-ui.ts`'s `AltUiCopy` is everything else — the hero, the feature grid, install steps, the FAQ question/answer _templates_, section headings, and both closing CTAs — identical across all six comparison pages and the hub except for `{app}`. That third layer was the gap: `AppCopy` translated cleanly into all 7 locales while the surrounding template stayed English-only string literals in `scripts/gen-alternatives.ts`, so a "translated" `/de/myfitnesspal-mcp` page still greeted a German visitor in English everywhere except the per-app paragraphs. `alt-ui.ts`'s doc comment marks which fields are raw HTML (contain `<em>`/`<strong>` tags or pre-escaped `&amp;`/`&ldquo;`/`&rdquo;` entities, inserted unescaped) versus plain text (escaped at render time) — a translation must preserve every tag, entity, and placeholder token (`{app}`, `{link}`, `{copyUrl}`, `{apps}`) verbatim. `scripts/gen-alternatives.ts`'s `featuresBlock()`/`installBlock()`/`faqsFor()` read from `altUiFor(locale)` and substitute placeholders at render time; `FEATURE_ICONS` stays a fixed array in the generator (icons are structural, matched to `AltUiCopy.app.features` by index, never translated).

**Troubleshooting lives at the bottom of `/tools`** (`/tools#troubleshooting`, with a "Help" pill after the category pills, and a footer link from every page — `chrome.ts`'s `footer.troubleshooting`, which must equal each locale's `ToolsDoc.troubleshooting.title`, pinned by `src/site-copy.test.ts`), not on its own route: `ToolsDoc.troubleshooting` (`pillLabel`/`title`/`description` plus `items: Record<TroubleshootingId, TroubleshootingEntry>`, so typecheck fails for a locale missing an entry), in the order of `TROUBLESHOOTING_IDS` in `src/copy/tools.ts`. Each id is the `<details>` DOM id, never translated, and deep-links (`/tools#wrong-day` opens that entry via the small script in `gen-tools.ts`). `answerHtml` is trusted, unescaped HTML that may link only to `#anchors` (a tool id or another troubleshooting id), `https://` or `mailto:` — never a site-relative `/…` path, because plain data has no `pathFor()` and a translated page would link back to English. No FAQPage JSON-LD. The copy restates constants from the code — `LIMIT_PER_WINDOW`, `AUTH_LIMIT_PER_WINDOW`, `BAN_STRIKE_THRESHOLD` and `BAN_DURATIONS_MS` (`src/rate-limit.ts`), `SESSION_TTL_MS` and `REFRESH_TOKEN_TTL_SECONDS` (`src/oauth.ts`; the 24h access-token TTL is deliberately not stated, since refresh keeps a connection alive), `EXPORT_TTL_SECONDS` (`src/export.ts`) — so changing any of them means updating all 10 `tools*.ts` files and README's Troubleshooting section; `src/site-copy.test.ts` pins the numbers. Its prose `mailto:` and GitHub issues/security links are stripped by two `tools.html` rules in `scripts/depersonalize.ts`.

**Generators**: `scripts/gen-legal.ts` (privacy/terms), `scripts/gen-tools.ts` (`/tools`), `scripts/gen-index.ts` (the landing page), and `scripts/gen-alternatives.ts` (`/alternatives` + the 6 comparison pages) all follow the same shape — render English to `public/<file>` and every populated locale to `public/{locale}/<file>`. Re-run a generator after editing its data file; regenerate `public/sitemap.xml` via `scripts/gen-sitemap.ts` after that (it walks `PAGE_ROUTES` × `SITE_LOCALES` and only emits a `<url>` for a locale/page pair that actually exists on disk — an entry is a promise to crawlers, and a page that isn't built yet would 500). A fact repeated inside `nav()`/`footer()` is not owned by any single generator: editing `chrome.ts` means re-running all five generators, not just the one whose own data file changed, or every other page keeps the stale value while the one page you meant to fix is correct. `src/site-copy.test.ts` pins specific phrases (e.g. that caffeine is named everywhere the nutrient set is enumerated) directly against the _source data_ files (`src/copy/alt-ui.ts`, not `scripts/gen-alternatives.ts`) plus the regenerated HTML — so both the data and the regeneration have to be right, and the test survives content moving between generator and data file as it did here.

**In-prose cross-links are a trap**: a `LegalDoc` paragraph that links to the _other_ legal doc (e.g. privacy → terms) can't call `pathFor(locale, ...)` itself — it's plain data, not a template — so it's written as `href="/terms" data-legal-link="terms"` and `scripts/gen-legal.ts`'s `localizeCrossLinks()` rewrites the href to the locale-correct path at render time. Forgetting this is exactly how a translated page ends up silently linking back to the English version (caught once already, live, before this existed).

**hreflang/canonical**: `scripts/site-partials.ts`'s `localeHead(locale, suffix)` emits a self-referencing canonical (never canonical-to-English — that tells Google the translation is a duplicate) plus reciprocal `hreflang` links for every `SITE_LOCALES` entry, `x-default` → English, and `og:locale`/`og:locale:alternate`. `nav()` also renders a language switcher (a `<details>`/`.lang-switch` disclosure, light-dismissed via `site.js`) from the same reciprocal-URL data. `src/alt-pages.test.ts` asserts hreflang is fully reciprocal and every canonical is self-referencing, scoped to generator-produced pages (detected by `generatedBanner()`'s HTML comment) — which by now is every page, `index.html` and `tools.html` included, since both moved off hand-authored HTML onto `gen-index.ts`/`gen-tools.ts`.

**Translation is fully AI-generated, no human review pass** (a deliberate choice, most consequential on `src/copy/legal.ts` — treat that file as the one most worth a native-speaker legal review before relying on it). Every translated page carries `TRANSLATION_NOTICE` (`src/routes.ts`) linking to the same page in English; the privacy policy and terms carry the stronger `LEGAL_TRANSLATION_NOTICE` instead (`translationNotice(locale, suffix, "legal")` in `gen-legal.ts`), which says the translation may contain mistakes and the English version is the one that applies. **Brand names are never inflected in any locale** ("w serwisie GitHub", "za pośrednictwem serwisu Patreon", not "na GitHubie"/"na Patreonie"; same for Claude, ChatGPT and the app names): besides reading as product names, `scripts/depersonalize.ts` matches the base forms only, and a Polish pass that declined GitHub and Patreon left the maintainer's links on a self-hoster's `pl/terms.html`. `public/llms.txt` stays English-only (it's an AI-crawler ingestion doc, not a search-engine surface) but names the translated locales in prose. `scripts/depersonalize.ts` discovers `public/{locale}/*.html` at run time (mirroring how it already discovers `public/alternatives/*.html`) so a self-hoster's GA tag / GitHub links / contact email get stripped from every locale, not just English.

**`public/login.html` is translated too, but it's a genuinely different case** — it has zero SEO surface (reachable only via `GET /authorize`, not in the sitemap, `<meta name="robots" content="noindex, nofollow">`) and no fixed URL to hang a locale prefix off of: it's rendered per in-flight OAuth session by `renderLoginPage()` in `src/oauth.ts`, not routed by path. `scripts/gen-login.ts` + `src/copy/login.ts` follow the same typed-data-and-generator pattern as everywhere else, but the generated file is still a _template_ — `{{SESSION_ID}}`/`{{ERROR}}` (unchanged) plus `{{LANG_SWITCHER}}` and `{{LANG_SWITCHER_MENU}}` tokens that `nav()`'s `dynamicSwitcher` option emits in place of the normal static header switcher and the sheet menu's language grid (the grid is the only switcher a phone gets, since `.head-tools` is hidden below 700px), because this page's switcher links have to carry the in-flight session's `state`/`redirect_uri`/`client_id` (reconstructed by `authorizeUrl()` in `oauth.ts`), not a fixed `pathFor()`. A `{{CLIENT_NOTICE}}` token under the page's subtitle is replaced per session by `renderClientNotice()` with the consent notice naming where the user will be sent back (see "OAuth" above); its three strings are `LOGIN_CLIENT_NOTICE` in `src/copy/login.ts` (one `LOGIN_CLIENT_NOTICE_<LOCALE>` per `login.<locale>.ts`), each keeping its `{host}` placeholder verbatim. `OAuthSession` carries a `locale` field, chosen once at `GET /authorize` (from an optional `?locale=` query param the switcher sets — clicking a switcher link re-enters `/authorize` and mints a fresh session, which is fine since nothing's been submitted yet) and reused for every re-render of that same flow (a failed password or Google sign-in) so an error doesn't silently snap the page back to English. The email form has two submit buttons, `action=signin` (`LoginDoc.signInButton`) and `action=signup` (`LoginDoc.createAccountButton`); see "Sign-up is an explicit action" under OAuth. Locale _availability_ is checked by file existence on disk at request time (`availableLoginLocales()`), not by importing `src/copy/login.ts`'s `LOGIN` keys — deliberately mirroring how `src/index.ts`'s static locale routes decide availability, so oauth.ts doesn't need to import the content module. Every error the page shows is translated (`LOGIN_ERRORS` in `src/copy/login.ts`): the two Google-flow strings plus `invalidCredentials`, `signInFailed`, `weakPassword`, `passwordTooLong`, `emailInvalid` and `signUpFailed`, chosen by the typed error `code`. Supabase Auth's own message text is never rendered — it is untranslated third-party text, and on the sign-in path it would reveal whether an address has an account.
